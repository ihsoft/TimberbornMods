# External Automation API

Copy `AutomationApi.cs` into your mod. Do not reference AdvancedAutomation.dll.
The helper depends only on standard .NET types and the game's Bindito.Core, Timberborn.BaseComponentSystem and
UnityEngine (logging).

Create one helper per Game context, using the injected IContainer, your stable provider ID and a localization key
for your mod's name. Register capabilities in IPostLoadableSingleton.PostLoad, before Automation binds saved rules.
Do not register from constructors or wait for the first value change.
Provider and capability IDs must start with an ASCII letter and contain only ASCII letters and digits
(`[A-Za-z][A-Za-z0-9]*`). IDs are case-sensitive. Invalid IDs are rejected, not renamed or encoded.
This restriction does not apply to localization keys, display names or string option values.

The first registration of a signal or action wins. Automation logs each later registration with the same provider ID,
capability ID and kind as an error and ignores it without throwing; remaining registrations continue normally.
Different provider IDs do not conflict. A signal and an action may share an ID.

```csharp
_automation = new AutomationApi(container, "ExampleMod", ModNameLocKey);

// In PostLoad:
_automation.AddSignal("Count", CountNameLocKey, () => service.Count);
_automation.AddAction("Reset", ResetNameLocKey, () => service.Reset());

// After your state changes:
_automation.UpdateSignal("Count");
```

The helper works without Automation installed. Registration resolves an optional versioned endpoint; calls with no
endpoint are no-ops. No getter is called by registration or UpdateSignal. Keep your normal game logic independent.
If the endpoint is not found, the helper logs one INFO message per instance with the provider ID and supported contract
(`Automation.ConnectV1`). This also applies when Automation is not installed.

For a string dropdown, pass `options: [(value, nameLocKey), ...]`. Values and capability IDs are stable save contracts.
For actions, the label may include `{0}` to display the argument in compact rule descriptions.

AddSignal and AddAction have overloads for bool, int, float, double and string. Convert enums and custom structures
to one of these types in your getter or action. Numeric values use a signed 32-bit fixed-point representation with
two decimal places; int input must also fit that scaled range. Values outside this representation are errors.
Boolean values appear as On/Off. Actions accept zero or one argument.
Numeric signals and actions accept optional min/max for editor input only. These bounds do not reject or clamp
signal values or action arguments at runtime, including expressions entered in the script editor.
For action lambdas, specify the parameter type when needed to select an overload, for example `(double value) => ...`.

## Building capabilities

```csharp
var pumps = _automation.ForBuildings<MyPump>();
pumps.AddSignal("Pressure", PressureNameLocKey, pump => pump.Pressure);
pumps.AddAction("SetPressure", SetPressureNameLocKey,
                (MyPump pump, float value) => pump.SetPressure(value), min: 0, max: 10);

// In the provider's own update logic:
_automation.UpdateSignal("Pressure", pump);
```

MyPump must derive from the game's BaseComponent. A building must support Automation to host rules.
Capability IDs are provider-wide even across different ForBuildings groups.
Pass any component belonging to the same GameObject when notifying a building signal. Omit the source for globals.

## Percentages

Use AddPercentSignal and AddPercentAction for float or double values displayed as percentages. The same methods are
available on building helpers. Getters, action arguments and min/max use fractions: 0.75 means 75%, and 1 means 100%.

```csharp
_automation.AddPercentSignal("Fill", FillNameLocKey, () => service.FillRatio, min: 0, max: 1);
_automation.AddPercentAction("SetFill", SetFillNameLocKey,
                             (double value) => service.SetFillRatio(value), min: 0, max: 1);
```

The UI displays and accepts whole percentages; the step is one percentage point. With min: 0 and max: 1, the editor
accepts 0..100% for comparison thresholds and action arguments. Without bounds it also accepts negative percentages and
values above 100%. Runtime values are never clamped or checked against these editor bounds. Regular float and double
overloads display numbers instead of percentages. Double does not increase Automation's two-decimal precision.

## Deferred updates

All API calls run on the game thread. UpdateSignal only queues a possible change; it never evaluates getters or rules
on the caller's stack. Automation samples the latest state in a later rendered frame, after its load activation gate.
It coalesces updates per source, reads only observed sources, compares values, and notifies rules on changes.
Updates generated by actions wait for a subsequent pass. There is no polling fallback and no promise to deliver every
intermediate value. Use a counter when repeated occurrences need to be represented as state.

You may call UpdateSignal as often as needed, even when the value has not changed. For best game performance, call it
as rarely as practical: notify when your mod's logic indicates that the value may have changed, preferably in response
to an event rather than on every tick. Do not add elaborate change tracking just to avoid redundant notifications;
Automation already compares values internally.

Getters must be side-effect free. Automation may also read them while initializing a rule or showing the editor.
Actions may change game state normally; notify affected signals through UpdateSignal.
